# FTA System Monorepo 整理设计

- 状态：用户已批准（2026-09-12）
- 日期：2026-09-12
- 目标分支：`refactor/v2-monorepo`
- 变更类型：仓库结构迁移，不改变产品功能与业务语义

## 1. 当前事实

远程仓库 `main` 是当前可追踪的 Git 基线。经逐文件哈希对比，远程仓库与本地旧工作区的 Python 后端、API 文档和主要项目说明一致；本地旧工作区额外保留了 Vue 前端源码、评测代码、评测数据与大量生成物。

本地旧工作区没有有效提交历史，且缓存、运行输出、构建产物和源码混合存在，因此只作为缺失资产的恢复来源，不作为新的 Git 真源。

已确认的差异：

- 核心 Python 后端：两边一致。
- Vue 前端：仅本地旧工作区存在。
- `evaluation/`：仅本地旧工作区存在。
- `.env`、`__pycache__/`、`outputs/`、Vue `dist/`：属于配置或生成物，不进入迁移结果。
- 远程仓库已跟踪 `.env` 和若干临时文件，后续迁移时需要停止跟踪，但不得泄露其内容。

## 2. 产品与仓库边界

本仓库采用单仓库、前后端分离的组织方式。一个 Git 仓库承载同一产品的 Web 前端、Python AI 引擎、评测资产和共享文档。

第一轮只整理现有内容：

- 纳入 Vue 前端源码。
- 将现有 Python 服务迁入独立目录。
- 纳入可复现的评测脚本、数据集和精选基线报告。
- 建立根级启动说明、忽略规则和目录职责。

第一轮明确不做：

- 不创建没有业务实现的 Java 空工程。
- 不修改现有 API 语义、Prompt、FTA 算法或数据库模型。
- 不修复现有回归测试中的业务失败。
- 不引入消息队列、微服务治理或新的前端框架。
- 不把历史运行输出和全部评测中间结果当作源码提交。
- 不在用户复核完整差异前推送 GitHub。

## 3. 目标目录

```text
Fta_system/
├─ frontend/                 # Vue 3 Web 前端
│  ├─ public/
│  ├─ src/
│  ├─ package.json
│  └─ package-lock.json
├─ backend-python/           # FastAPI 与 AI/FTA 引擎
│  ├─ *.py
│  ├─ examples/              # 可公开、可复现的请求与示例文档
│  ├─ requirements.txt       # 从真实导入关系形成的依赖清单
│  └─ .env.example
├─ evaluation/               # 离线评测，不参与生产请求链路
│  ├─ data_correction/
│  └─ quality_eval/
├─ docs/                     # 对外架构、API、运行和评测说明
├─ .gitignore
└─ README.md
```

以下目录只在出现真实内容时创建：

```text
backend-java/                # 后续 Spring Boot 业务平台
contracts/                   # 跨 Java/Python/前端的 OpenAPI 合同
deploy/                      # 可实际验证的容器与部署配置
```

不创建空目录来假装系统已经拥有尚未实现的能力。

## 4. 模块 Owner

### `frontend/`

负责页面、交互、客户端状态和 API 展示适配。它只消费后端返回的结构化事实，不拥有故障树生成规则、检索结论或评测指标定义。

迁移来源为旧工作区 Vue 工程。保留 `src/`、`public/`、包清单、锁文件和构建配置；保留源码真实引用的图片与视频。排除 `dist/` 和本地依赖缓存。

### `backend-python/`

负责当前 FastAPI、文件解析、模型调用、知识图谱适配、FTA 生成与导出。第一轮保持现有 Python 文件之间的相对关系，以目录移动为主，避免在仓库整理中同时重写业务逻辑。

### `evaluation/`

负责数据修正、质量评测、数据集和指标计算。评测层只能观察和调用生产能力，不得成为生产解析规则或指标结果的第二 owner。

只保留能够解释来源和复现方法的数据集、脚本与必要基线。多次重复运行生成的报告和图片不全部纳入长期真源。

### 根目录与 `docs/`

根目录只保留仓库入口、许可证、忽略规则和跨模块说明。API、部署、评测方法和架构说明进入 `docs/`。

现有无扩展名项目说明文件 `pppppp` 拟整理为可识别的项目说明文档；现有 Docker 文档只有在配置能够实际运行时才继续作为当前文档，否则标记为历史说明。具体重命名和归档属于本设计的一部分，实施前由用户通过本文复核确认。

## 5. 数据流与接口边界

第一轮不改变现有数据流：

```text
Vue 前端
  -> FastAPI HTTP 接口
  -> 文件解析 / LLM 抽取 / Neo4j / FTA 构建
  -> JSON、DOT、XML、PNG 与报告结果
```

前端 API 地址继续通过环境配置或现有开发代理提供，不在源码中新增机器专用绝对路径。

未来 Java 服务加入后，预期边界为：

```text
Vue 前端
  -> Java 业务平台（身份、项目、任务、审计）
  -> Python AI 引擎（解析、检索、推理、FTA）
```

Java 加入前必须先形成真实 OpenAPI 合同；本轮不提前维护两套接口。

## 6. 迁移策略

迁移在独立分支完成，按以下顺序进行：

1. 建立根级 `.gitignore`，先阻断密钥、缓存、运行输出和构建产物进入 Git。
2. 将远程现有 Python 后端移动到 `backend-python/`，保持内容和运行语义不变。
3. 从本地旧工作区恢复 Vue 源码到 `frontend/`，只复制构建需要的源文件和真实引用资源。
4. 从本地旧工作区恢复评测代码、数据集和精选基线到 `evaluation/`。
5. 更新脚本与文档中的相对路径、启动目录和模块说明。
6. 根据实际导入生成 Python 依赖清单；前端继续以锁文件作为依赖真源。
7. 执行后端、前端、评测和敏感文件检查。
8. 向用户展示完整差异与验证证据；得到明确确认后才允许推送远程分支。

迁移不使用“复制全部目录后再删除”的方式，避免把旧工作区中的缓存、密钥和历史生成物带入远程仓库。

## 7. 安全与隐私

- `.env` 永不提交，仓库只保留无真实凭证的 `.env.example`。
- 提交前扫描常见 API Key、Token、密码和私钥模式。
- Vue 中使用的媒体文件在提交前检查体积、版权来源和必要性。
- 评测数据在提交前确认不包含个人信息、客户私有资料或真实生产秘密。
- 不把本机绝对路径写入公开 README、配置或运行结果。

## 8. 验收标准

### Git 与目录

- 工作发生在 `refactor/v2-monorepo`，`main` 不被直接改写。
- `git status --short` 中不存在 `.env`、`__pycache__`、`outputs/`、`dist/`、IDE 配置或临时文件。
- 后端迁移应主要表现为 Git rename；非路径变化需要逐项解释。
- 不存在嵌套 Git 仓库。

### Python 后端

- Python 源码能够完成语法检查。
- API 应用能够在按依赖文档建立的干净环境中导入。
- 现有回归脚本的迁移后结果与迁移前基线一致；已知 AOCS 用例失败必须明确记录，不能伪装成全绿。
- 示例请求中的相对路径和输出路径可在新目录下工作。

### Vue 前端

- 使用锁文件安装依赖。
- 生产构建成功。
- 首页和工作台能够真实渲染。
- 前端请求指向可配置的后端地址，不依赖旧电脑绝对路径。

### 评测

- 评测脚本可导入，数据集路径正确。
- 项目说明引用的基线报告在仓库中存在。
- 历史报告只证明历史运行；若未重新执行，不宣称为当前验证结果。

### 文档

- 根 README 能说明目录职责、环境要求、启动顺序和最小演示流程。
- API、评测和部署文档只描述仓库中真实存在且验证过的能力。
- 不保留指向不存在的 `app.py`、镜像、目录或评测文件的当前说明。

## 9. 风险与停止条件

最大风险是目录移动同时改变 Python 导入、前端 API 地址或评测相对路径，导致“文件看起来更整齐但系统无法运行”。因此第一轮禁止顺手重构核心算法，以基线一致性和可复现启动作为停止条件。

第一轮完成的定义：前端、Python 后端和评测资产进入清晰目录；敏感文件与生成物被排除；后端基线行为无新增回归；前端构建通过；根 README 可以指导重新启动；完整差异经用户确认后才推送。

## 10. 学习协作机制

本项目同时承担技术学习目标。实施不是一次性代写，而采用“问题—原理—判断—实现—验证—复盘”的循环：

1. 每个任务开始前说明它解决的真实问题、owner 边界和相关底层知识。
2. 在关键设计点向用户提出一个可回答的问题，先了解用户当前判断；不知道或答错不阻断任务。
3. 实现过程中保持改动小且可验证，让代码证据对应讲解内容。
4. 验收后总结技术取舍、失败路径和可用于面试表达的项目事实。
5. 学习问题集中在真实触达的主题，不为覆盖“八股”而给系统堆入无需求的中间件。

第一轮迁移对应的学习主题包括 Git 真源与生成物、Monorepo 边界、Python 导入与工作目录、Node 依赖锁、环境变量与密钥、构建产物、基线测试与回归证据。后续业务重构再逐步进入 HTTP、并发、数据库、检索、LLM 评测和 Java/Python 服务边界。
